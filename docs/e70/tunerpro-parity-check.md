# TunerPro parity check (60 seconds, do this before trusting block tables)

Our Python tools and TunerPro both read the same XDF, but the XDF format is **not publicly
documented**. For ordinary (non-strided) tables there is no ambiguity and the two agree. For the
**strided block tables** — the ones that show five gear pairs side by side — `xdflib` uses a column
pitch of `(rowcount - 1) * elementsizebits + minorstridebits`, a convention derived by matching the
firmware, not from any specification. If TunerPro computes a different address, then the same edit
made in TunerPro and in our tools writes **different bytes**.

This check settles it. You need TunerPro, the XDF, and a stock E70 read.

## The test

1. Open `8hpe70_cali_v3.xdf` in TunerPro with a stock E70 calibration loaded.
2. Open the table **`Upshift lines, char 00: 1>2..5>6`**.
3. Read the **first column** (`1>2`), top to bottom.

**Expected (correct) values — 15 rows:**

```
325  325  325  325  325  450  475  700  725  875  900  1100  1100  1100  1100
```

The five columns should read, in their bottom row (pedal 1100): `1100, 1900, 3000, 3950, 5150`.

These values are independently confirmed three ways: the firmware's own shift-line grammar recovered
by decompiling the reader functions, the per-gear-pair single-curve tables in the same XDF that
alias the same flash bytes, and our decoder.

## Reading the result

**Column 1>2 matches exactly** — TunerPro and our tools agree. Block tables are safe to edit in
either, and binaries generated by both are interchangeable. Nothing to do.

**Column 1>2 shows anything else** — TunerPro resolves strided addresses differently from `xdflib`.
Then:

- Do **not** edit the `... lines, char NN: A>B..C>D` block tables in TunerPro; its view of them is
  wrong and saving would corrupt unrelated bytes.
- Use the per-gear-pair single curves instead (`Upshift char 00: 1>2`, `Downshift char 00: 2>1`,
  …). These are plain packed 15×1 tables with no strides, they are unambiguous, and they alias
  exactly the same flash bytes as the blocks.
- Tell the tooling side: the fix is to regenerate the block tables without strides (or drop them),
  so that both programs read the same bytes.

Either way, run the safety gate on any bin before flashing — it refuses anything that touches a byte
no XDF item covers:

```sh
/usr/bin/python3 tools/xdf_verify.py 8hpe70_cali_v3.xdf stock.bin tuned.bin
```

## Why the single curves are the safe default

The XDF deliberately exposes the same flash bytes twice: once as multi-column blocks (convenient for
seeing a whole characteristic at once) and once as individual per-gear-pair curves. Editing either
changes the same bytes. The single curves carry no stride fields at all, so every tool that can read
an XDF reads them identically. When in doubt, edit the curves.
